
### MQTT

|方式|端口|谁用|典型场景|
|---|---|---|---|
|**MQTT publish**（Java/MQTTX）|8883 / 8084|设备、业务服务|正常收发|
|**REST API publish**（`/api/v5/publish`）|8443|另一套系统|用 HTTP 往 MQTT 里"塞"一条消息|

两者最终都进同一个 broker、都路由给订阅者。区别只是**入口通道不同**：正常设备走 8883/8084；只有当你"另一套后端服务想用 HTTP 方便地推一条 MQTT 消息"时才用 8443 —— 属于辅助/集成手段，不是设备的标准做法。


### 协议

| 协议头      | 全称           | 加密了吗？      | 主要用途               | 典型端口     | 和 MQTT 有关系吗？ |
| -------- | ------------ | ---------- | ------------------ | -------- | ------------ |
| `tcp://` | 普通 TCP       | **否** (明文) | 设备直接连 MQTT         | 1883     | 是（最原始）       |
| `ssl://` | 加密 TCP       | **是**      | 设备安全连接 MQTT        | **8883** | **是（强烈推荐）**  |
| `ws://`  | WebSocket    | 否          | 网页连 MQTT           | 8083     | 是（但需特殊框架）    |
| `wss://` | WebSocket 加密 | **是**      | 网页安全连接 MQTT        | **8084** | 是（网页端推荐）     |
| `ssh://` | 安全外壳         | **是**      | **远程登录 Linux 服务器** | **22**   | **否（不要搞混！）** |

#### ConcurrentHashMap 方法

| 操作方法             | 是否加锁                       | 原因                                      |
| ---------------- | -------------------------- | --------------------------------------- |
| **`get`（读）**     | **❌ 基本无锁**                 | 利用 `volatile` 和不可变性，保证读取安全，不加锁能极大提升并发度。 |
| **`put`（写空桶）**   | **❌ 无锁（CAS）**              | CAS 原子操作直接尝试插入，不阻塞其他线程。                 |
| **`put`（写非空桶）**  | **✅ 加锁（synchronized 头节点）** | 必须锁住头节点，防止多线程同时修改同一个链表/树，导致数据错乱。        |
| **`remove`（删除）** | **✅ 加锁（synchronized 头节点）** | 删除必须保证原子性，防止删错或链表断裂。                    |


- **Java编译器（javac）**：**前端编译**。发生在你**写代码时**，点下"Run"或执行`mvn compile`的那一瞬间。它的输入是`.java`源文件，输出是`.class`字节码文件。
    
- **JIT编译器（Just-In-Time）**：**后端运行时编译**。发生在**程序启动后运行中**。它的输入是`.class`字节码，输出是**CPU能直接执行的机器码（native code）**
- **javac（静态编译）**：只会"低头看"你写的**这一个类**。它只做语法检查、变量类型校验、把语法糖（如泛型、增强for循环）解糖。它**完全不知道**你的系统压力大不大，不知道CPU是Intel还是ARM。
    
- **JIT（动态编译）**：会"抬头看"**整个程序的运行状态**。它知道哪些代码是"热点"（频繁调用），知道CPU的流水线特性，甚至知道内存里对象的分布。**它是基于"运行数据"来做优化的**，而javac只是基于"语法规则"。
