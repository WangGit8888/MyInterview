#### 缓存问题
1、缓存穿透:

缓存穿透是指查询一个一定不存在的数据，如果从存储层查不到数据则不写
入缓存，这将导致这个不存在的数据每次请求都要到 DB 去查询，可能导致
DB 挂掉。这种情况大概率是遭到了攻击。

如何解决:

RDB是一个快照文件，它是把redis内存存储的数据写到磁盘上，当
redis实例宕机恢复数据的时候，方便从RDB的快照文件中恢复数据。

### Redis是单线程的，但是为什么还是那么快

1、完全是基于内存的,C语言编写
2、采用单线程，避免了不必要的上下文切换可竞争条件
3、使用多路I/O复用模型,非阻塞IO

##### I/O多路复用

I/O多路复用是指利用单个线程来同时监听多个Socket ，并
在某个Socket可读、可写时得到通知，从而避免无效的等待，充分利用CPU
资源。目前的I/O多路复用都是采用的epoll模式实现，它会在通知用户进程
Socket就绪的同时，把已就绪的Socket写入用户空间，不需要挨个遍历
Socket来判断是否就绪，提升了性能。


### 数据类型

| 数据类型                 | 底层实现                            | 一句话用途             |
| -------------------- | ------------------------------- | ----------------- |
| **String**           | SDS（简单动态字符串）                    | 缓存对象、分布式锁、计数器     |
| **Hash**             | ziplist / hashtable             | 存储对象字段，如用户信息、购物车  |
| **List**             | quicklist（ziplist + linkedlist） | 消息队列、最新消息列表       |
| **Set**              | intset / hashtable              | 去重、标签、抽奖、共同好友     |
| **ZSet（Sorted Set）** | ziplist / skiplist + hashtable  | 排行榜、延时队列、带权重的任务调度 |
| **Bitmap**           | String 的位操作                     | 签到、活跃用户统计、布隆过滤器   |
| **HyperLogLog**      | 概率数据结构                          | UV 统计、去重计数（允许误差）  |
| **Stream**           | 消息队列（类似 Kafka）                  | 可靠的消息队列、消费组、消息回溯  |

#### 底层实现

| 类型         | 底层数据结构                                           | 关键点                             |
| ---------- | ------------------------------------------------ | ------------------------------- |
| **String** | **SDS**（Simple Dynamic String）                   | 预分配空间、O(1) 获取长度、二进制安全           |
| **Hash**   | 元素少时用 **ziplist**（压缩列表），元素多时升级为 **hashtable**    | ziplist 省内存，hashtable 支持快速查找    |
| **List**   | **quicklist**（ziplist 组成的双向链表）                   | 结合了 ziplist 省内存和链表快速插入的优点       |
| **Set**    | 元素全是整数用 **intset**，否则用 **hashtable**             | intset 省内存，hashtable 支持 O(1) 查重 |
| **ZSet**   | 元素少时用 **ziplist**，元素多时用 **skiplist + hashtable** | **跳表**实现有序，**哈希表**实现 O(1) 查分数   |

##### 为什么ZSet使用跳表而不是红黑树:

ZSet 之所以用跳表不用红黑树，是因为跳表实现简单、支持范围查询（ZRANGE）效率高，而且并发场景下更容易维护。

#### Redis三种过期删除策略

1. 定时删除(主动删除)
2. 惰性删除(被动删除)
3. 定期删除(主动批量删除)

Redis实际采用的方案：惰性删除 + 定期删除

#### 内存淘汰策略

| 淘汰策略                 | 说明                        |
| -------------------- | ------------------------- |
| `noeviction`         | 不淘汰，内存满时写操作直接报错（默认）       |
| `allkeys-lru`        | 从所有 key 中淘汰最近最少使用的        |
| `volatile-lru`       | 从设置了过期时间的 key 中淘汰最近最少使用的  |
| `allkeys-random`     | 从所有 key 中随机淘汰             |
| `volatile-random`    | 从设置了过期时间的 key 中随机淘汰       |
| `volatile-ttl`       | 从设置了过期时间的 key 中淘汰 TTL 最短的 |
| `allkeys-lfu`（4.0+）  | 从所有 key 中淘汰最不经常使用的        |
| `volatile-lfu`（4.0+） | 从设置了过期时间的 key 中淘汰最不经常使用的  |

### 布隆过滤器

#### 实现区别

| 对比维度     | **Guava 布隆过滤器**                    | **Redisson 布隆过滤器**          |
| -------- | ---------------------------------- | --------------------------- |
| **存储位置** | **JVM 堆内存**（本地内存）                  | **Redis 服务器**（分布式存储）        |
| **作用范围** | **单机**，仅供当前 JVM 进程使用               | **分布式**，所有客户端共享同一个过滤器       |
| **持久化**  | 程序重启后**丢失**                        | 存储在 Redis 中，**不丢失**         |
| **适用场景** | 单机应用、缓存穿透防护（本地缓存场景）                | 分布式系统、微服务间共享、大流量抗压场景        |
| **性能**   | 极快（纯内存访问，无网络开销）                    | 相对较慢（每次操作需网络 IO + Redis 计算） |
| **外部依赖** | 无（Guava 是 Java 库）                  | 依赖 Redis 服务                 |
| **底层实现** | **`AtomicLongArray`** (即 `long[]`) | **Bitmap**（String）          |

### 分布式锁

#### Redisson分布式锁

**基于Redis(Hash)的Lua脚本原子性 + 看门狗（Watchdog）自动续期 + 可重入计数**

Redisson分布式锁的核心是Lua脚本保证原子性，底层采用Hash数据结构实现可重入。

它的关键特性是看门狗（Watchdog），默认锁30秒，业务没完成时每10秒自动续期，避免了业务超时锁被误删。

在生产环境的主从架构下，锁会有短暂的失效风险（主节点宕机数据未同步），Redisson提供的Redlock红锁可以解决，但出于性能和复杂度考虑，在大多数业务场景下我们不会启用红锁，而是依赖业务幂等性做兜底
