
### 如何停止线程
1、interrupt:设个标志
2、isInterrupted:只看不擦
3、interrupted:看完就擦,只能问自己

// 示例
Thread t = new Thread(() -> {
    // 第一次调用 interrupted()
    System.out.println(Thread.interrupted());  // false（初始为 false）
    
    Thread.currentThread().interrupt();        // 设置中断标志
    
    System.out.println(Thread.interrupted());  // true（返回 true，然后清除标志）
    System.out.println(Thread.interrupted());  // false（已被清除）
    
    System.out.println(Thread.currentThread().isInterrupted()); // false
});
t.start();

### interrupt() 和 isInterrupted()

中断标记 + 阻塞 = 抛异常

中断标记 + 运行中 = 只改标志，不抛异常

#### AQS

AQS（AbstractQueuedSynchronizer，抽象队列同步器） 是 Java 并发包java.util.concurrent）的基石，是一个用于构建锁和同步器的框架。它通过一个 volatile int state 状态变量和一个 FIFO（先进先出）双向等待队列，提供了资源共享的原子性管理和线程阻塞/唤醒机制。

核心机制：通过 CAS（Compare And Swap）操作原子性地修改 state 值。如果线程获取资源（如锁）失败，它会被包装成一个 Node 节点，加入到 AQS 的 FIFO（先进先出）等待队列中并被阻塞。

#### AQS为什么要用双向链表单向的行不行?

双向链表让 AQS 可以随时从任意节点往前或往后走，处理取消排队和唤醒操作时无需遍历整个队列，性能更高、代码更安全。

#### AQS下公平非公平

| 同步器                        | 是否支持公平/非公平        | 原因                     |
| -------------------------- | ----------------- | ---------------------- |
| **ReentrantLock**          | ✅ **支持**（可选）      | 独占锁，锁竞争激烈时，业务可能关心谁先获得锁 |
| **Semaphore**              | ✅ **支持**（可选）      | 共享锁，资源许可的获取顺序在某些场景很重要  |
| **CountDownLatch**         | ❌ **不支持**         | 门闩打开后所有线程一起放行，顺序无意义    |
| **CyclicBarrier**          | ❌ **不支持**（不用 AQS） | 所有线程互相等待，同时到达屏障点，顺序无意义 |
| **ReentrantReadWriteLock** | ✅ **支持**（可选）      | 读锁/写锁的获取顺序可能影响业务公平性    |

### concurrentHashMap

在JDK1.8中，放弃了Segment臃肿的设计，数据结构跟HashMap的数据结构是一 样的：数组+红黑树+链表 
采用 CAS + Synchronized来保证并发安全进行实现 

1. CAS控制数组节点的添加 
2. synchronized只锁定当前链表或红黑二叉树的首节点，只要hash不冲突，就不 会产生并发的问题 , 效率得到提升

#### 扩容是多线程的么
ConcurrentHashMap 的扩容机制是"支持多线程协同"，而不是"必须多线程"。第一个触发的线程会单线程启动扩容，后续感知到扩容的线程会主动加入帮忙。这种设计既保证了单线程场景下的简单高效，又利用了高并发场景下的多核优势。

##### 为什么扩容只能是2的次幂

用位运算替代取模，极致性能。

哈希表的核心操作是：hashCode → 数组下标。常规做法是取模运算：index = hashCode % length。但取模（%）是数学运算，在CPU层面需要除法指令，相对较慢。

#### ThreadLocal + 多线程 产生数据污染

java只可能是多任务对单线程,不可能是单任务对多线程。

数据污染不是"一个任务换线程"导致的，而是"一个线程换任务"导致的。ThreadLocal 的定位是'当前线程的上下文变量'，它的生命周期是跟随当前线程的'当前执行任务'的。

线程池中的线程是复用的，但每个任务是独立的。清理掉旧数据后，下一次任务执行时，业务代码的入口处（比如拦截器或 AOP）会重新将'本次请求的新数据' set 进去。

Spring 通过 `ThreadLocal` 将连接和线程绑定，不同线程天然隔离。
#### synchronized锁升级

|锁状态|适用场景|底层实现|性能开销|
|---|---|---|---|
|**无锁**|没有线程竞争|无|最低|
|**偏向锁**|同一线程多次重入|对象头中记录线程ID|很低|
|**轻量级锁**|少量线程交替竞争（无阻塞）|CAS + 自旋|中等|
|**重量级锁**|大量线程竞争（有阻塞）|操作系统 mutex|最高|

`sychronized` 在锁升级的不同阶段，公平性表现不一样：

|锁状态|公平性|原因|
|---|---|---|
|**偏向锁**|无意义|只有一个线程，没有竞争|
|**轻量级锁**|非公平（CAS 抢）|通过 CAS 自旋抢占，谁抢到谁执行|
|**重量级锁**|**近似公平**|依赖操作系统的 `pthread_mutex`，底层维护了一个**等待队列（WaitSet）**，线程被唤醒时基本按队列顺序|

### synchronized 对比 Lock

| 对比维度        | **synchronized**                                                               | **Lock (如 ReentrantLock)**                                                                                |
| ----------- | ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| **实现层面**    | **JVM 内置关键字**，底层由 JVM 的监视器（Monitor）实现，自动释放锁。                                   | **Java API 接口**，由 `java.util.concurrent.locks` 包提供，需要手动 `unlock()`。                                       |
| **锁的获取与释放** | **自动**：进入同步代码块自动获取锁，退出（包括抛出异常）自动释放锁。                                           | **手动**：必须用 `lock()` 获取，`unlock()` 释放，**强烈建议在 `finally` 块中释放**，防止死锁。                                       |
| **灵活性**     | **低**：要么获取锁执行，要么阻塞等待，无法尝试获取锁。                                                  | **高**：提供 `tryLock()`（尝试获取，失败立即返回）、`tryLock(long time, TimeUnit unit)`（超时获取）、`lockInterruptibly()`（可中断获取）。 |
| **公平性**     | **非公平锁**。新来的线程有机会插队，不能设置为公平锁。                                                  | **支持公平和非公平**。`ReentrantLock(boolean fair)` 构造器参数可指定公平锁（但公平锁性能通常较低，默认非公平）。                                 |
| **等待中断**    | **不支持**。使用 `wait()` 等待时，线程不能被中断（`InterruptedException` 不会抛出）。                  | **支持**。`lockInterruptibly()` 允许在等待锁的过程中响应中断，可避免死锁后的无限等待。                                                  |
| **锁绑定条件**   | 只能有一个等待队列（`wait/notify`），一个锁只能绑定一个条件。                                          | **支持多个 Condition**。一个 `ReentrantLock` 可以 `newCondition()` 多次，实现精准唤醒（如生产者-消费者模式中，可以单独唤醒消费者，而不唤醒生产者）。       |
| **性能**      | **早期 JDK 1.6 前较差**，但 JDK 1.6 引入了 **偏向锁、轻量级锁、重量级锁** 等锁升级机制（锁膨胀），优化后性能与 Lock 相当。 | 适用于高竞争场景，但在低竞争场景下由于需要维护 AQS（队列同步器），开销略大于 synchronized                                                     |
### synchronized 原理

Synchronized【对象锁】采用互斥的方式让同一时刻至多只有一个线程能持
有【对象锁】它的底层由monitor实现的，monitor是jvm级别的对象（ C++实现），线程获
得锁需要使用对象（锁）关联monitor在monitor内部有三个属性，分别是owner、entrylist、waitset其中owner是关联的获得锁的线程，并且只能关联一个线程；entrylist关联的
是处于阻塞状态的线程；waitset关联的是处于Waiting状态的线程。

### 创建线程池有几种方式

Java 创建线程池主要有两种方式：通过 Executors 工具类或直接使用 ThreadPoolExecutor 构造函数。但我们生产环境只用后者，因为前者存在 OOM 风险。我们会在配置类中定义 ThreadPoolTaskExecutor Bean，手动设置核心线程数、最大线程数、有界队列和合理的拒绝策略，同时暴露监控指标。对于不同的业务场景，我们会拆分独立的线程池做隔离。

### AQS公平/非公平锁

非公平锁中，线程抢锁失败后不会立即入队，而是先通过tryAcquire再尝试一次（包含重入判断）。两次都失败后，才会通过addWaiter将当前线程封装成独占Node节点，CAS尾插法加入双向链表。入队后，在acquireQueued中自旋尝试抢锁，若前驱为头节点且抢锁成功则出队，否则LockSupport.park(this)阻塞。

非公平锁释放时，只唤醒head.next一个线程，而不是全部唤醒。非公平的‘不公平’体现在：队列中有等待线程时，新来的线程可以直接CAS抢锁（插队），而公平锁会先判断队列是否有前驱等待者，有则直接入队。
