
#### 预警模块

我负责的智慧工地模块需要对接海康ISC平台接收预警。海康的预警推送有一个特点——突发性很强，比如某个工人误入禁区，会在短时间内收到大量重复预警。而且预警后我们要同时做三件事：存库、发站内信、发短信通知。

最初是同步串行处理，接口响应要800多毫秒，而且短信接口偶尔超时会导致整个预警处理失败。

后来我引入了RabbitMQ做改造：

海康预警进来后直接发到MQ，立即返回200给海康，响应时间降到120ms

使用Topic Exchange把预警同时路由到三个队列：落库、站内信、短信

落库队列用手动ACK，确保消息不丢

短信队列配置重试机制，失败后自动重试3次，间隔5秒，仍然失败进入死信队列，由运维人工兜底

为了防止同一个预警重复处理，我还结合Redis存储了预警ID的幂等性校验

改造后，短信接口故障完全不影响预警核心功能，系统稳定性大大提升。


#### 人力资源库对接

这个功能是对接朗新天霁的人力资源库，核心目标是把他们系统中的人员档案、工作经历、教育经历等数据同步到我们自己的数据库中。

**整体流程是这样的：

朗新那边分配了一个租户ID，我们用这个ID加上固定的账号密码，调用他们的人员列表分页接口。接口支持按 pageSize 和 pageNum 分页，响应中会返回 total 总记录数，我们通过循环分页拉取到所有的人员ID。

拿到这批ID后，我们使用线程池并发调用三个子接口——基本信息接口、工作经历接口、教育经历接口。之所以用线程池，是因为如果串行处理，几万条数据耗时太长，而并发可以显著缩短同步窗口期。

但是，朗新的接口有限流限制：单个接口每分钟最多调用1000次。为了避免触发限流，我们用 Redis + Lua 实现了分布式令牌桶限流器，所有线程在调用前先去令牌桶获取许可。之所以不用 Guava 的 RateLimiter，是因为我们的服务可能多实例部署，Guava 是单机级的，无法在多实例间共享限流状态；而 Redis 方案的限流状态是全局统一的，更利于后续扩展。

整个同步流程通过 XXL-JOB 配置为每天凌晨1点定时触发，避开业务高峰期。

**异常处理方面：

对于接口超时等临时性异常，我们会自动重试最多2次。

对于字段超长、数据格式异常等无法自动恢复的问题，我们会把对应的ID记录到一张 error 表中，并触发告警通知开发人员。同时提供了补偿机制，支持开发人员修复问题后在管理后台手动重跑失败的数据。

**固定窗口->滑动窗口->令牌桶

固定窗口无法应对'边界突刺';滑动窗口只管总数不管分布;令牌桶管总数管分布;

#### 车辆出入洞

这里是主要功能是对现场的隧洞内出入车辆做记录；这里基于xxjob做了一个定时任务，每10秒同步一次，把现场的闸机的进出数据同步到record表里；这里的闸机分进场进洞出洞出场的，两层，这里的需求是根据闸机记录统计出各个洞的最新的车辆状态分洞内和洞外，进场了但没进洞属于洞外；这里的实现是获取车辆的record数据然后根据车牌号分组，单一车牌只保留最新的闸机记录，最后记录是进洞的判定为洞内，最后记录为出洞、进场则判定为洞外，其他不计，然后这边在总览页面做了一个统计图统计的洞内外的车辆，并罗列了这些车辆是挂在哪些标段上的。
